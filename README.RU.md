# d2-diagram

**Одной строкой:** просишь у AI-ассистента схему, получаешь исходник `.d2` строк
на сорок и `.png` — оба коммитятся рядом с кодом, который описывают.

| Для чего | Не для чего |
|---|---|
| архитектура — что где выполняется и что кого зовёт | графики: bar, line, scatter, Gantt — осей в D2 нет |
| графы модулей и импортов, циклы между пакетами | Венн, пирамида, воронка, radar, treemap |
| путь запроса с условием на каждом переходе | разовая красивая картинка для слайда |
| классы, модели данных, код против своих таблиц | всё, где смысл несёт координата или площадь |
| слои Terraform, топология Kubernetes, потоки CI | |

Картинка должна жить в git и меняться вместе с кодом — это сюда. Должна быть
красивой один раз — не сюда.

---

Попросишь ассистента нарисовать схему архитектуры — получишь одно из двух: блок
Mermaid, который рендерится, но выглядит как все остальные блоки Mermaid, либо
несколько сотен строк SVG с расставленными вручную координатами, которые больше
никто никогда не поправит.

Этот скилл идёт третьим путём. Ассистент пишет несколько десятков строк на
[D2](https://d2lang.com), координаты считает движок раскладки, рядом с исходником
коммитится PNG. Схема живёт в git, меняется тем же pull request, что и код, и её
diff можно прочитать.

Работает с Claude Code, Opencode и Codex. Собрано и проверено на Linux;
бинарники под macOS существуют и ветка под них в установщике есть, но сам
установщик на Маке никто не запускал.

[English version](README.md)

## Зачем

Схема устаревает быстрее любой другой документации, потому что поправить её
дороже, чем не заметить. Две привычки делают только хуже:

- **Картинка без исходника.** SVG, нарисованный руками, нельзя изменить, не
  проделав работу заново. Поэтому его и не меняют — и через месяц он описывает
  систему, которой больше нет.
- **Исходник, который никто не читает.** Пятьсот строк `<path d="M…">` в pull
  request рецензент не разбирает. Изменение проходит непроверенным.

D2 решает обе задачи тем, что разделяет их. Добавить компонент — одна строка:

```d2
private: Private subnets {
  eks: EKS node group
  rds: RDS Postgres {shape: cylinder}
}

internet -> public.alb: ":443"
public.alb -> private.eks: ":8080"
private.eks -> private.rds: ":5432"
```

Координаты — не твоя забота. D2 отдаёт граф движку раскладки, и оба движка,
которые он умеет использовать, уже лежат внутри бинарника — ставить нечего:

```console
$ d2 layout
dagre (bundled) - The directed graph layout library Dagre
elk (bundled) - Eclipse Layout Kernel (ELK) with the Layered algorithm.
```

Dagre стоит по умолчанию и хорош на деревьях и потоках; ELK, из проекта Eclipse,
лучше справляется со слоёной инфраструктурой. Переключается флагом
`--layout=elk` или строкой в файле. В любом случае в pull request видно
`+ rds: RDS Postgres`, а не стену чисел.

## Установка

```bash
git clone https://github.com/vadbosh/d2-diagram.git
cd d2-diagram
./install.sh              # во все найденные IDE
./install.sh --dry-run    # показать, что будет сделано
```

Скилл ставится в `~/.claude/skills/d2-diagram`,
`~/.config/opencode/skills/d2-diagram` и `~/.codex/skills/d2-diagram` — в те из
них, которые существуют. Не установленный ассистент пропускается, а не
создаётся.

Без бинарника `d2` скилл бесполезен, поэтому его отсутствие установщик
предлагает исправить: определяет последний релиз под твою ОС и архитектуру и
распаковывает его в `~/.local/bin`. В терминале сначала спрашивает, по умолчанию
«нет»; `--with-d2` пропускает вопрос, `--no-d2` убирает предложение.

Бинарник есть под Linux и macOS, и под Intel, и под ARM. Проверено на текущем
релизе `v0.7.1` — каждый из архивов отдаётся с кодом 200:

```
d2-v0.7.1-linux-amd64.tar.gz    20 МБ
d2-v0.7.1-linux-arm64.tar.gz    19 МБ
d2-v0.7.1-macos-amd64.tar.gz    20 МБ
d2-v0.7.1-macos-arm64.tar.gz    19 МБ
```

На macOS установщик первым делом тянется к Homebrew, потому что тот впереди: в
формуле сейчас **0.8.1**, а последний релиз на GitHub — 0.7.1, тег v0.8.1
поставлен без бинарников. Если brew нет, установщик откатывается к архиву.

```bash
brew install d2        # это и запустит установщик на Маке с brew
```

У разработчиков есть и однострочник `curl … | sh`. Здесь он не используется и не
рекомендуется: подать скачанный скрипт прямо в оболочку — значит выполнить всё,
что отдал сервер, а тот же результат достигается одним архивом:

```bash
tag=$(curl -fsSL https://api.github.com/repos/terrastruct/d2/releases/latest \
      | sed -n 's/.*"tag_name" *: *"\([^"]*\)".*/\1/p' | head -1)
curl -fsSL -o d2.tar.gz \
  "https://github.com/terrastruct/d2/releases/download/$tag/d2-$tag-linux-arm64.tar.gz"
tar xzf d2.tar.gz
install -m 0755 "d2-$tag/bin/d2" ~/.local/bin/d2
```

Замени `linux-arm64` на свою платформу из списка выше.

Подробности, флаги и проверка — [docs/install.ru.md](docs/install.ru.md).

## Как пользоваться

Вызывать нечего. Запусти сессию в том репозитории, который надо нарисовать, и
попроси обычными словами — скилл срабатывает на саму просьбу.

**1. Открой ассистента там, где лежит код.**

```bash
cd ~/work/my-service
claude          # или: opencode / codex
```

**2. Попроси схему и скажи, на какой вопрос она должна отвечать.**

Вторая половина и отличает полезную схему от коллажа из прямоугольников. Сравни
«нарисуй архитектуру» и «покажи, какие сервисы ходят в базу и какие из этих
вызовов идут через кэш»: первое приглашает нарисовать всё, у второго есть ответ,
который может оказаться верным или неверным.

Запросы, которые работают как написаны, — скопируй и поменяй пути:

```
На основании кода в этом репозитории нарисуй схему модулей и того, как они
работают с базой. Положи в docs/diagrams/.

Нарисуй архитектуру: что где выполняется и что кого вызывает. Читай код,
не угадывай.

Покажи импорты между пакетами в src/ и есть ли там циклы. Рёбра достань
анализатором зависимостей.

Нарисуй путь HTTP-запроса от балансировщика до базы и отметь, что должно быть
верно на каждом переходе.

Схему модели данных: слева типы TypeScript, справа таблицы Postgres, чтобы
было видно, где они расходятся.

Перерисуй этот блок Mermaid в D2 и положи в docs/diagrams/.
```

### Terraform — особый случай: граф уже существует

Для инфраструктуры никого не надо просить читать `.tf` глазами. Terraform умеет
печатать собственный граф зависимостей, а состояние знает, что развёрнуто на
самом деле. Скажи это в запросе — и схема перестанет быть чьим-то толкованием:

```
Построй схему по `terraform graph`, а не по чтению файлов.

Нарисуй то, что развёрнуто на самом деле, а не то, что написано в
конфигурации: возьми ресурсы из `terraform state list` и `terraform show -json`.

Нарисуй, как корневые модули зависят друг от друга: рёбра — это блоки
`terraform_remote_state`, по одному на каждое чтение чужого состояния.
```

Откуда это берётся и что печатает на самом деле — первое воспроизводится в любом
временном каталоге, ни облачного аккаунта, ни провайдера не нужно:

```hcl
# /tmp/tf-demo/main.tf
resource "terraform_data" "network" { input = "vpc" }

resource "terraform_data" "cluster" {
  input      = "eks"
  depends_on = [terraform_data.network]
}

resource "terraform_data" "workload" {
  input      = terraform_data.cluster.output
  depends_on = [terraform_data.cluster]
}
```

```console
$ terraform init && terraform graph
digraph G {
  rankdir = "RL";
  node [shape = rect, fontname = "sans-serif"];
  "terraform_data.cluster" [label="terraform_data.cluster"];
  "terraform_data.network" [label="terraform_data.network"];
  "terraform_data.workload" [label="terraform_data.workload"];
  "terraform_data.cluster" -> "terraform_data.network";
  "terraform_data.workload" -> "terraform_data.cluster";
}
```

Это и есть весь вход, нужный для схемы: узлы и рёбра, уже правильные, без чьего-либо
толкования `.tf`. Отдай это и попроси картинку.

`terraform state list` и `terraform show -json` отвечают на другой вопрос — что
лежит в состоянии, а не что написано в конфигурации. Им нужен каталог с
инициализированным бэкендом, поэтому самодостаточного примера здесь нет: при
написании этого текста обе команды запускались на живом модуле и вернули перечень
ресурсов и полный JSON, но тот вывод — чья-то инфраструктура, и он не приводится.

Блоки `terraform_remote_state` — это рёбра между корневыми модулями в слоёном
репозитории. Это не общее рассуждение, а то, как собран пример из поставки: в
[`examples/cluster-layers.d2`](examples/cluster-layers.d2) по одному ребру на
каждый блок, найденный грепом из
[docs/patterns.ru.md](docs/patterns.ru.md#рёбра-берутся-из-кода-а-не-из-памяти).

Вклад скилла поверх любого из этих источников — читаемость, а не сам граф. Первый
пример нарисует и `dot`; он только не сгруппирует по корневым модулям, не отметит
то единственное, что сейчас заменяется, и не уложится в колонку README.

**3. Что делает ассистент.**

Сначала читает настоящий исходник — файлы `.tf`, импорты, манифесты, миграции, —
а не вспоминает, как обычно выглядит проект такой формы. Потом пишет исходник,
собирает картинку и показывает её:

```
docs/diagrams/
├── theme.d2            общие цвета и стили линий, их подключают остальные
├── architecture.d2     исходник — его правят и рецензируют
└── architecture.png    то, на что ссылается README
```

**4. Правки — словами, а не в графическом редакторе.**

Исходник — сорок строк, поэтому исправления дёшевы и конкретны:

```
Слишком широкая для README — разверни вертикально.
Убери роли IAM, они здесь ничего не добавляют.
Отметь очередь оранжевым, её как раз заменяют.
Добавь worker, он читает ту же базу.
```

**5. Вставь в свой README.**

```markdown
[![Архитектура](docs/diagrams/architecture.png)](docs/diagrams/architecture.png)
```

Картинка обёрнута ссылкой на себя, чтобы клик открывал её целиком: страницу
SVG-файла GitHub не открывает, поэтому коммитится PNG.

После любой правки `.d2` попроси пересобрать картинку: исходник и изображение
коммитятся вместе, и устаревший PNG — единственная поломка, которую эта схема
работы всё ещё допускает.

## Что скилл добавляет поверх D2

D2 — это язык, а скилл — рабочая практика вокруг него, и почти всё в ней выросло
из того, что однажды пошло не так:

- **Палитра в одном файле.** Tailwind slate, синий хребет, оранжевый акцент;
  каждая схема подключает её строкой `...@theme`. Поменял один файл — изменилось
  оформление всех.
- **PNG, и никогда SVG, если картинка идёт на GitHub.** Встроенный SVG виден, но
  клик по нему приводит на страницу, которую GitHub рендерить отказывается: у
  читателя остаётся мелкая картинка, которую нельзя увеличить. Скилл встраивает
  PNG, обёрнутый ссылкой на себя, а SVG держит как промежуточный файл в `/tmp`.
- **Никаких markdown-подписей.** Блок `|md` компилируется в `<foreignObject>` —
  элемент SVG, который вставляет внутрь картинки произвольный HTML. Санитайзер
  GitHub отвергает любой SVG с ним, и выглядит это как сломанный файл, а не как
  вопрос оформления.
- **Пропорции как обязательная проверка.** Колонка README — примерно 900 пикселей,
  поэтому холст 4:1 нечитаем, каким бы хорошим ни было содержание. Смени
  `direction:` и посмотри размер холста в атрибуте `viewBox` в первой строке
  собранного SVG — туда D2 записывает, насколько крупной вышла картинка.
- **Рёбра берутся из кода, а не из памяти.** Из блоков `terraform_remote_state`,
  из `madge`, из `pyreverse`. Граф зависимостей, нарисованный по памяти, врёт в
  тот день, когда кто-то добавил импорт.
- **Честная граница.** D2 не нарисует диаграмму Венна, пирамиду, radar и вообще
  ничего, где смысл несёт координата или площадь. Скилл говорит об этом прямо и
  называет, чем это делать вместо него, — чтобы никто не потратил час, выгибая
  его в воронку.

## Галерея

Четыре схемы, сделанные скиллом; исходник и картинка лежат рядом в
[`examples/`](examples/). Клик открывает полный размер — ровно ради этого
коммитится PNG.

### Корневые модули Terraform и порядок применения

[![Корневые модули](examples/cluster-layers.png)](examples/cluster-layers.png)

Исходник: [`examples/cluster-layers.d2`](examples/cluster-layers.d2) — 66 строк.
Рёбра — чтения `terraform_remote_state`, вытащенные из кода, а не вспомненные.
Оранжевое ребро отмечает единственное, что сейчас заменяется, — то, на что
читатель должен посмотреть первым.

### Путь запроса через Kubernetes Gateway

[![Путь запроса](examples/cluster-request-path.png)](examples/cluster-request-path.png)

Исходник: [`examples/cluster-request-path.d2`](examples/cluster-request-path.d2).
У каждого узла назван RESOURCE, которым он спрашивается, у каждой стрелки —
условие перехода, включая симметричное: настроишь одну сторону без другой, и
соединение рвётся.

### Монорепозиторий на TypeScript — граф пакетов

[![Граф пакетов](examples/ts-monorepo.png)](examples/ts-monorepo.png)

Исходник: [`examples/ts-monorepo.d2`](examples/ts-monorepo.d2). Ничего
инфраструктурного здесь нет: контейнеры — рабочие области, рёбра — импорты, а
оранжевая пара — цикл, найденный анализатором зависимостей.

### Сервис на TypeScript — типы и таблицы за ними

[![Модель данных](examples/ts-domain-model.png)](examples/ts-domain-model.png)

Исходник: [`examples/ts-domain-model.d2`](examples/ts-domain-model.d2). Работают две встроенные фигуры D2: `class` рисует UML-подобную коробку с полями
и методами, `sql_table` — таблицу с типами колонок и метками `PK`/`FK`. Рёбра
прицеплены к отдельным колонкам. Нарисованы вместе потому, что именно так проявляется тихое расхождение
между типом в коде и колонкой в базе.

## Тесты

```bash
./tests/test_render.sh
```

Собирает каждый пример из поставки, проверяет, что ни один не породил
`<foreignObject>`, валидирует тему и сверяет, что все описанные в скилле стилевые
классы действительно существуют. Без `d2` набор пропускается, а не падает.
